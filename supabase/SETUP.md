# 무료 클라우드 연결

## 1. Supabase 프로젝트 생성

supabase.com에서 무료 프로젝트를 생성합니다. DB 비밀번호는 프로젝트 설정에 안전하게 보관하고 GitHub 또는 채팅에 넣지 마세요. 이 앱은 회사 한 곳의 직원들이 동일한 데이터를 공유하는 구성입니다.

## 2. DB 설치

새 프로젝트의 SQL Editor에서 `supabase/schema.sql` 전체를 한 번 실행합니다. 테이블, 중복/날짜 검사, 관계, RLS, 직원 확인, 관리자 삭제 권한 및 트랜잭션 RPC를 만듭니다. 이미 동일 이름의 테이블이 있다면 기존 DB를 삭제하지 말고 별도 마이그레이션을 검토하세요.

## 3. 직원 계정 만들기

Authentication 설정에서 **Allow new users to sign up**을 끕니다. Authentication → Users에서 **Add user → Create new user**로 직원 계정을 생성합니다. 비밀번호는 별도의 안전한 경로로 직원에게 전달합니다. 직원 화면은 **아이디/비밀번호**로 로그인합니다. 아이디는 영문·숫자·밑줄·하이픈으로 3~32자이며 대소문자는 구분하지 않습니다.

Supabase는 내부적으로 이메일 형식의 식별자를 요구하므로 **아이디@flow.invalid**로 계정을 만듭니다. 예: 직원 아이디 `admin` → Users의 Email 입력값 `admin@flow.invalid`. `flow.invalid`는 실제 메일이 전달되지 않는 내부 식별용 예약 도메인입니다. 메일 발송·이메일 인증을 사용하지 않습니다. 계정 생성 시 **Auto Confirm User**를 켜고, 이메일 초대 대신 Create new user를 사용하세요. 직원은 웹앱에 `admin`만 입력합니다.

기존 이메일 계정이 있다면 자동 변환되지 않습니다. 기존 계정의 UUID와 flow_members 연결을 유지한 채 Supabase의 지원되는 사용자 관리 기능으로 이메일을 `아이디@flow.invalid`로 변경하고 확인 상태를 유지해야 합니다. 기존 계정을 무작정 삭제하지 마세요. 새 계정을 만들 경우 새 UUID에 관리자/직원 역할을 별도로 부여해야 합니다.

config.js의 usernameEmailDomain을 변경할 경우 내부 계정의 도메인도 같아야 합니다. 실제 메일 수신과 셀프서비스 복구가 필요하면 소유한 도메인 및 이메일 발송/복구 기능을 별도로 구성해야 합니다. 사용자 스스로 가입하거나 초대 메일 링크에서 비밀번호를 설정하는 화면은 없습니다.

Users 화면에서 사용자 UUID를 복사한 뒤 SQL Editor에서 아래를 실행합니다. UUID는 본인의 실제 사용자 ID로 바꿉니다.

```sql
insert into public.flow_members(user_id, role)
values ('사용자-UUID', 'admin');
-- 다른 직원은 'admin' 대신 'employee'를 사용합니다.
```

관리자·직원 모두 조회/등록/수정할 수 있고 삭제는 관리자만 가능합니다. 권한은 화면뿐 아니라 DB에서도 강제됩니다. 계정을 중단하려면 해당 사용자의 flow_members 행을 삭제하고 Auth 계정을 비활성화하세요. 자기 자신을 관리자로 등록할 수 있는 공개 API는 없습니다.

비밀번호 재설정은 관리자 대시보드에서 처리합니다. 셀프서비스 재설정 및 비밀번호 변경 화면은 후속 기능입니다. 사용자 계정을 직원마다 따로 생성하고 공유 계정을 사용하지 마세요.

## 4. 공개 연결 설정

Project Settings의 API/Data API/API Keys 화면에서 Project URL과 **publishable key**(또는 legacy anon key)를 확인해 루트의 `config.js`에 입력합니다.

```js
window.FLOW_CONFIG = {
  usernameEmailDomain: 'flow.invalid',
  supabaseUrl: 'https://프로젝트ID.supabase.co',
  supabasePublishableKey: 'sb_publishable_공개키'
};
```

이 두 값은 브라우저에 공개되는 설정입니다. `service_role`, `sb_secret_` 키, DB 비밀번호는 넣지 마세요. 데이터 보호는 직원 인증, RLS 및 RPC 권한 검사로 처리합니다.

## 5. GitHub Pages

GitHub 저장소 Settings → Pages → Deploy from a branch → master / (root) → Save.

배포 후 `https://adh9608.github.io/web-study/`에서 직원 계정으로 로그인합니다. Authentication URL Configuration의 Site URL도 위 주소로 설정합니다. URL을 설정하는 것만으로 비밀번호 재설정 화면이 구현되는 것은 아닙니다.

## 검증

- 로그인 없이 제품/고객 데이터를 읽거나 변경할 수 없어야 합니다.
- Auth 계정만 있고 flow_members에 없는 사용자는 접근할 수 없어야 합니다.
- 관리자가 제품/고객/출고를 등록한 뒤 다른 직원과 다른 기기에서 동일한 데이터가 보여야 합니다.
- 직원은 삭제할 수 없어야 합니다. 직접 RPC를 호출해도 삭제가 거부되어야 합니다.
- 중복 시리얼/고객코드/출고 및 접수일 이전 완료일이 DB에서 거부되어야 합니다.
- 같은 항목을 동시에 수정하면 먼저 저장한 정보가 덮어써지지 않고 뒤 요청에 갱신 안내가 표시되어야 합니다.
- 오래된 값이 보이면 새로고침 버튼을 사용합니다. 자동 실시간 동기화는 아직 없습니다.

기존 브라우저 저장 데이터는 유지하지만 DB에 자동 업로드하지 않습니다. 설정이 비어 있을 때 로그인 화면의 ‘기존 브라우저 데이터 보기’에서 CSV를 백업할 수 있습니다. 클라우드 초기 DB는 비어 있습니다. 데이터 이전은 별도로 준비해야 합니다.

## 무료 플랜 및 백업

요금제의 데이터·트래픽 제한과 비활성 프로젝트 중지 정책은 Supabase의 현재 정책을 확인하세요. 무료 플랜의 자동 백업/복구 보장을 전제로 운영하지 마세요. 정기적으로 DB를 별도 백업하고 복구 방법을 확인해야 합니다. 화면의 CSV는 목록 내보내기이며 완전한 DB 복구용 파일이 아닙니다.

실제 프로젝트에서 SQL 실행 및 직원 로그인/저장 검증이 완료되기 전에는 운영 연결 완료로 보지 않습니다.

## 기존 DB: 시리얼번호 자동 생성 업데이트

이미 DB가 설치되어 있다면 **schema.sql을 다시 실행하지 말고** `supabase/migrations/20261013_customer_codes.sql` 전체를 SQL Editor에서 실행합니다. 새 프로젝트의 schema.sql에는 이 기능이 포함되어 있습니다.

- 제품 구분: 0=레일방제기, 1=레일리프트, 2=미스트
- 형식: `SN` + 제품 구분 + 생산일 `YYMMDD` + 최소 4자리 누적 순번
- 예: `SN02610130001`, `SN02610139999`, `SN026101310000`
- 날짜가 바뀌어도 구분별 순번은 계속 증가하며, 삭제한 제품의 순번은 재사용하지 않습니다.
- 등록 화면에서 **자동 생성 / 수기 입력**을 선택합니다. 자동 생성은 저장 시 DB가 번호를 확정하고, 수기 입력은 입력한 번호를 그대로 저장합니다. 중복 번호는 대소문자와 앞뒤 공백을 정리해 검사합니다.
- 번호에 포함된 제품 구분·생산일은 자동 생성 제품에서 수정할 수 없습니다. 모델명과 기타 정보는 수정할 수 있습니다.
- 기존 번호 및 출고/A/S 연결은 그대로 유지됩니다. 기존 번호가 위 형식이면 해당 구분의 최대 순번부터 이어집니다. 그 외 기존 제품은 미분류 상태로 유지하며 구분만 나중에 지정할 수 있습니다.
- 마이그레이션을 여러 번 실행해도 카운터는 초기화되지 않습니다.
- 자동 생성 업데이트 전 DB라면 새 제품 등록을 차단합니다. 자동 생성만 설치된 DB에서는 자동 등록은 가능하고 수기 입력은 비활성화됩니다. 최신 manual_serial SQL을 실행하면 두 방식 모두 사용할 수 있습니다.

DB에 없는 과거 생산 이력이 있다면 새 제품 등록 전에 구분별 최종 순번을 맞춰야 합니다. SQL Editor에서 현재 값을 확인합니다.

```sql
select category, last_number from public.flow_serial_counters order by category;
```

예를 들어 레일방제기를 이미 350대 생산했다면 다음을 실행합니다. 실제 마지막 순번으로 바꾸세요. 이 코드는 기존 카운터를 낮추지 않습니다.

```sql
begin;
select pg_advisory_xact_lock(83421671);
update public.flow_serial_counters
set last_number = greatest(last_number, 350)
where category = '0';
commit;
```

Auth 공개 키로는 DB 마이그레이션을 실행할 수 없습니다. 프로젝트 소유자가 SQL Editor에서 실행한 뒤 앱을 새로고침해야 합니다.

### 수기 시리얼 입력 업데이트

기존 자동 생성 버전을 설치했다면 `supabase/migrations/20261013_customer_codes.sql`을 실행하세요. 이 파일은 기본 DB에도 적용 가능하며 앞선 auto_serial 파일을 따로 실행할 필요가 없습니다. 최신 업데이트 후 이전 auto_serial.sql을 다시 실행하면 수기 기능이 제거되므로 실행하지 마세요.

새 제품 등록 시 입력 방식을 ‘수기 입력’으로 바꾸고 시리얼번호를 입력합니다. 기존 번호와 중복되면 저장이 거부됩니다. 예: `OLD-HS-001`처럼 자유로운 번호도 사용할 수 있습니다.

수기 번호가 `SN02610139999`처럼 자동 생성 형식이라면 구분 숫자는 선택한 제품 구분과 같아야 하고, 해당 구분의 카운터를 적어도 9999로 올립니다. 다음 자동 번호는 날짜와 무관하게 10000 이상으로 생성됩니다. 일반 수기 번호는 카운터를 증가시키지 않습니다. 등록 후 시리얼번호는 변경되지 않습니다.

## 고객코드 자동 생성 / 수기 입력

기존 프로젝트에서는 최신 통합 업데이트인 **`supabase/migrations/20261013_customer_codes.sql`** 전체를 SQL Editor에서 실행합니다. 이전 시리얼 자동/수기 기능도 포함하므로 이 파일만 실행하면 됩니다. 기존 데이터와 번호, 출고·A/S 관계 및 누적 카운터는 유지됩니다. 업데이트 후 이전 auto_serial/manual_serial SQL을 다시 실행하지 마세요.

고객 등록 화면에서 ‘자동 생성’ 또는 ‘수기 입력’을 선택합니다.

- 자동: `C0001`부터 날짜와 관계없이 누적되며 `C9999` 다음은 `C10000`입니다.
- 기존 `C숫자` 형식의 고객코드를 검사해 가장 큰 순번 다음부터 생성합니다.
- 자동으로 배정한 코드는 고객 삭제 후에도 다시 자동 배정하지 않습니다.
- 수기: 기존 코드를 직접 입력하며 대소문자·앞뒤 공백을 정리해 중복을 검사합니다.
- 수기로 `C9999`를 입력하면 자동 카운터가 적어도 9999로 올라갑니다. 일반 문자 코드는 카운터를 올리지 않습니다.
- 등록 후 고객코드는 고정하고 고객명·주소·연락처·비고만 수정합니다.
- DB 업데이트 전에는 기존 수기 등록 화면을 유지합니다. 업데이트 후 웹앱을 새로고침하면 입력 방식 선택이 표시됩니다.

과거 고객코드가 DB에 없으면 SQL Editor에서 `flow_customer_counter`의 last_number를 확인하고 아래처럼 마지막 사용 순번 이상으로 올립니다. 350은 실제 마지막 순번으로 바꾸세요.

```sql
begin;
select pg_advisory_xact_lock(83421671);
update public.flow_customer_counter
set last_number = greatest(last_number, 350)
where id = 1;
commit;
```

## 수주관리 및 출고 연동

최신 통합 업데이트 **`supabase/migrations/20261013_orders.sql`** 전체를 SQL Editor에서 실행합니다. 이전 시리얼·고객코드 기능도 포함하며 기존 데이터와 번호를 유지합니다. 업데이트 후 이전 마이그레이션을 다시 실행하지 마세요. 새 프로젝트는 schema.sql에 모두 포함됩니다.

1. 수주관리에서 고객, 접수일, 납기일과 진행 상태를 등록합니다. 수주번호는 `SO0001`부터 누적 자동 생성합니다.
2. ‘품목 추가’로 모델명·사양·수량을 여러 줄 등록합니다. 같은 모델도 사양이 다르면 별도 품목으로 입력하세요.
3. 모델명·사양은 제품관리의 모델명·레일(사양)과 일치해야 합니다. 앞뒤 공백과 영문 대소문자는 출고 연결 시 구분하지 않습니다. 사양이 없는 품목은 빈칸으로 입력합니다.
4. 출고관리에서 ‘연결 수주 품목’을 선택합니다. 고객과 제품명이 자동으로 채워지고, 해당 모델·사양의 재고 시리얼만 선택 목록에 나옵니다.
5. 출고 기록 하나당 1대로 계산합니다. 여러 대를 나누어 출고해도 수량이 누적됩니다. 연결 없이 등록한 기존 출고는 수주 수량에 포함되지 않습니다. 기존 출고를 수정해 수주 품목에 연결할 수 있습니다.
6. 수주 목록에서 품목, 주문 수량, 출고 수량, 남은 수량을 확인합니다. 모든 품목이 출고되면 완료로 표시하며, 출고를 삭제하면 수량과 진행 상태가 다시 계산됩니다.

진행 상태는 접수·생산중·출고대기·취소를 입력하고, 완료는 전체 출고 수량으로 자동 판정합니다. 취소는 기록을 보존하며 취소된 수주에 새 출고를 연결할 수 없습니다. 이미 출고한 내역은 취소 후에도 남습니다. 재개하려면 수주 상태를 다시 변경합니다.

출고 이력이 있는 수주는 고객을 바꿀 수 없고, 이미 출고한 품목의 모델명·사양을 변경/삭제할 수 없습니다. 수량은 출고 수량 이상이어야 합니다. 관리자만 삭제할 수 있고, 출고 이력이 있는 수주는 삭제가 거부됩니다. 필요하면 취소로 기록을 남기세요.

직원은 등록·수정·취소가 가능하고 삭제는 관리자만 가능합니다. DB에서 과다 출고, 고객·모델·사양 불일치, 접수일 이전 출고와 동시 수정 충돌을 검사합니다. 출고가 변경되면 수주 버전도 갱신되므로 편집 중 충돌 안내가 나오면 다시 조회하세요.

최대 100개 품목을 한 수주에 등록하며 각 품목 수량은 1~1,000,000의 정수입니다. 금액·세금·발주서 파일 첨부·견적 기능은 포함하지 않습니다. DB 업데이트 전에도 기존 메뉴는 사용 가능하며 수주 등록은 업데이트 안내로 차단됩니다.
